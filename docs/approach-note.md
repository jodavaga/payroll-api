# How I Approached This Exercise

I read the code before writing anything, in the order the README suggests: `server.ts` first, then `report.ts` and `src/db/`. While reading, I added short comments directly in the code when I spotted something wrong (for example, in `report.ts` I marked the N+1 query and the lookup that never used its result). I did this before writing the final review document, as a way to capture issues in place first and organize them into a clear write-up later.

For Part 1, I focused on sorting issues by real impact instead of listing everything I could find. The most serious ones touch money or security directly (SQL injection, currencies mixed together in one total, money stored as floating-point numbers). Other issues are real but lower priority (missing validation, N+1 queries). And some things look strange but are not actual bugs (the mixed date formats, the in-memory database). Given the 1-hour time limit, I picked Option A for Part 2, since it builds on the most serious finding from the review and had a smaller scope than the cycle lifecycle option.

I used Claude Code (AI) as a pair-programming partner during the whole exercise. It did the first full read of the code and suggested the initial list of findings, but I made the key decisions myself, such as choosing that the global summary should only include `approved` cycles, not all cycles. I reviewed every change before accepting it. For Part 2, I made the overall code updates myself, and Claude Code then suggested improvements to the currency grouping, the new query, and the tests. One example: I had not thought about floating-point rounding errors, and Claude Code suggested using `Number.EPSILON` when rounding totals to avoid them. I reviewed each suggestion and applied the ones that made sense, instead of just accepting generated code without checking it.
